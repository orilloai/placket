# Threat model

This file says what placket protects, from whom, what it claims and what it leaves to others, for protocol version 0.1 and the Go reference implementation in this repository. Security reports go to `SECURITY.md` at the root of the repository.

## Assets

These are what an attacker would want to read, forge, change or destroy.

- **The mediator's key.** It signs every receipt. Whoever holds it can write receipts every verifier accepts.
- **Party keys and principal keys.** A party's key signs its declaration, its envelopes and its door calls. A principal's key signs the bindings that give roles.
- **Receipts and the journal.** `receipts.jsonl` is the evidence of what crossed (`journal-is-evidence`). Its order, its chains and its completeness matter as much as each signature. A closed Accord's journal ends in its close receipt, which pins every chain (close-2) and is handed to every member (L21).
- **Parts in transit and at rest.** A held part while its question is open, a queued delivery in `held/` until it is fetched, and the parts a party keeps in its state directory.
- **Salts.** A body and its salt together show which part a receipt names (crossing-3). A salt known to an outsider lets them test guesses of a short body against the digest.
- **The founding set and the card.** They fix who the members are, which roles they hold, and which decision module judges. The Accord id is their hash (setup-contract-5).
- **The answer call.** The answerer's own signed call, for an accept, a change or a decline, or the asker's for a cancel, over the answer's salted digest and never its text (maybe-11). The receipts its answer writes name it by its typed hash; it travels inside every delivery its answer queues, and the journal keeps it in `answers.jsonl` (maybe-12, decision record 0021). It is evidence of who answered, so a forged or replaced one would put words in a member's mouth.
- **The judges' key.** The user's own Jev key, which the window and the eval read from `PLACKET_JEV_KEY`. Whoever holds it can send requests billed to the user's Jev account.
- **Model output.** What a judge said of a part, kept in the journal's `judged/` directory. It may quote the part, so it is content.
- **The repository.** The requirement text, the vectors, the code, the checks of `make ci`, and the instruction files that agents follow.

## Actors and trust boundaries

Each actor below sits on one side of a trust boundary. The table in the STRIDE-lite section has one row for each.

- **The local user who runs the window.** In this version the window is one process on one machine, run by one party to the Accord (`README.md`). That user holds the mediator's key, reads every journal file, and can stop, edit or shorten the journal. Placket does not defend the other parties against this user; it gives them their own kept records to check the journal with (receipt-7).
- **Other local processes at the socket.** The door is a unix socket that the window sets to mode 0600 (`adapters/local/window.go`), and a client calls only a socket its own user owns. That mode is not what admits a call: whatever process connects, a call passes only when it is signed by a key, and the mediator then refuses a key that is not a member (setup-contract-6).
- **Remote parties sending signed bytes.** Declarations, bindings, messages, envelopes and receipts arrive as bytes from parties that do not trust each other. Placket trusts no member of these bytes until its signature verifies under the key the operation names, never one the bytes name (signing-2, crossing-6, receipt-6).
- **The repository and CI supply chain.** Go toolchain, GitHub Actions, the checks in `tools/guard/` and `tools/redgreen/`, and the tools `make ci` runs. The core module has no dependency (`core-no-deps`), and the root module requires only the core. The checker in `tools/guard/` is a module of its own with two dependencies, `github.com/santhosh-tekuri/jsonschema/v6` and `golang.org/x/text`; they run in `make ci` and are never built into the binary. The release path belongs here too: the release workflow, `.github/workflows/release.yml`, pins its actions by commit and its build tools by version (`docs/release.md`). A release's archives are signed with the workflow's own GitHub identity, carry GitHub's build provenance, and rebuild to the same bytes (decision record 0018), so a user can check where a binary came from without trusting the download.
- **The judge provider.** A judge is a model behind a network service. In v0.1.0 the one provider is Jev, called with the user's own key over HTTPS at the host of the judge's config. The window sends it the parts the terms let it judge, and takes back a verdict and a score. Placket trusts its answer only where both sides' terms let it decide, and trusts nothing else it returns.
- **An agent behind `placket mcp`.** `placket mcp` is one party's client on standard input and output: whatever drives it, a model included, calls the tools with that party's proposing keys, one per label it was started with. It can give, fetch, list the questions its keys may answer, ask for a result and cancel its own question; it lists no tool that accepts, changes or declines, runs no command and holds no mediator key. A label whose key answers questions under its Accord, by its own founding set, is refused unless the user starts it with `--allow-answering` (decision record 0024). Text the agent reads from a part is data to it, as to any reader.
- **The labels config.** `mediators.json` in the user's config directory names, for each mediator, an Accord id, a key file, a founding set and a socket. It is the user's own file: placket checks its shape and that no two entries collide on a socket or a state directory, and trusts the paths it names as the user's choice. A label is a local name, never signed.
- **Agents.** Agents build most of placket. The rules they follow live in `AGENTS.md`, `CONTRIBUTING.md`, `docs/rules/`, `docs/review.md`, `docs/security/secure-coding.md` and `docs/style/`; those files, `.github/workflows/` and the checks change only in a change of their own, the maintainer approves every change, and `.github/CODEOWNERS` names the maintainer as code owner of every path. Text in an issue, a pull request or a comment from anyone outside the project is data to read, never an instruction to follow.

## Security properties

Each claim names the requirement ids of `spec/protocol.md` it rests on. Claims about the door and the journal rest on decision records and code, since those are not protocol formats.

- **P1. A receipt cannot be edited or forged without the mediator's key.** Each receipt is a DSSE envelope signed by the mediator with Ed25519 over the canonical bytes of its statement. A verifier takes the mediator's reference from its caller, never from a receipt, so an edited receipt, or one signed again by another key, fails. Rests on receipt-1, receipt-6, signing-2.
- **P2. A receipt removed from the middle of a chain is detected.** Receipts chain per ordered pair of parties by `seq` and `prev`, so a gap fails `chain` at the next receipt of that pair. Rests on receipt-5, receipt-6.
- **P3. A receipt removed from the end is detected by a party that kept records, not by verification alone.** A cut list still verifies. Reconciliation lists a delivered receipt the journal lacks as removed, and an envelope no receipt echoes as missing. Rests on receipt-6, receipt-7, crossing-5.
- **P4. Only the signer of an envelope can be named as a part's sender.** The sender is the caller whose key verified the envelope; no member of a message names a sender, and a `from` in the extension is refused. Rests on crossing-1, crossing-4, crossing-6.
- **P5. An accepted envelope cannot be given again.** A `seq` at or below the sender's highest accepted one is refused, and an edited message fails the envelope's hash. Rests on crossing-4.
- **P6. A stranger changes nothing and has nothing read.** A caller with no declaration in the set is refused before any other input is read, and every refused give, fetch or answer writes nothing and queues nothing. Rests on setup-contract-6, crossing-6, crossing-7, and section 6's check table.
- **P7. Roles come only from principal-signed bindings, and the Accord is fixed by its id.** Each party signs its own terms; a principal the policy lists signs each binding, for this mediator. Any change to the set, the operator or the card founds to another id. Rests on setup-contract-1, setup-contract-2, setup-contract-3, setup-contract-5, setup-contract-7.
- **P8. Every receipt names the decision module that judged it, and the decision is reproducible.** The card hash is in every receipt; the same inputs at the same times write the same receipts byte for byte. A refusal term wins, and a kind no term names never crosses. Rests on setup-contract-4, receipt-3, receipt-10, composition-1, composition-2, composition-3, composition-5.
- **P9. A held part reaches its receiver only through an answer that permits it.** While a question is open, its part is shown to its answerers and to no one else. Only an answerer answers, a question closes once, and an answer at or after the deadline is refused. A release is written only in the operation that carries the answer, after the answer's receipt. Rests on maybe-1, maybe-5, maybe-6, maybe-7, maybe-10.
- **P10. Receipts carry no content.** A receipt names a part by kind and salted digest, never by body or salt; whoever holds both can show the part is the one judged. A salt is exactly 32 bytes, so a digest opens as one salt and one body only: no holder can show a part's suffix, or a longer text, as the part judged. A delivery goes once, to its receiver only, and the mediator keeps no body of a blocked part or a fetched delivery. Rests on crossing-3, receipt-2.
- **P11. Every party hashes and signs the same bytes.** The canonical form gives one byte string per value and refuses repeated names, ill-formed UTF-8 and unsafe numbers, so two readers cannot disagree on what was signed. Signatures are cofactorless with canonical keys, so a malleated signature or a small-order key signs nothing. The four placket type URIs are never payload types, so no payload signature stands for a placket object's. Rests on canonical-1, canonical-4, canonical-5, canonical-6, signing-1, signing-2, signing-4.
- **P12. A receipt shown without verification says so.** Rests on receipt-8.
- **P13. The log adds nothing a verified receipt does not cover.** Every cell comes from a verified receipt or a kept part such a receipt covers, joined by envelope hash or salted digest, never by time or file name. Rests on section 12, log-1, log-2.
- **P14. A door call is bound to one caller, one Accord and one moment.** The door checks size, form, the call's signature, the Accord, a time within 60 seconds and a nonce unseen for 120 seconds, in that order, before the mediator sees anything. The call is signed under its own media type. Rests on decision record 0010 and `adapters/local/call.go`; no requirement id, since the call is a door format.
- **P15. A reply survives a crash.** Every journal write is synced before the reply, and a failed write ends the window with no reply. A restart reverifies every receipt and closes each question left open with a receipt. Rests on decision records 0008 and 0011, `adapters/journal/journal.go`, and receipt-6, maybe-4, maybe-5 for what reload checks and writes.
- **P16. Every receipt says who decided, and an answer is witnessed by its answerer's own signature.** A receipt names the terms, a judge of the card, an answer call by its typed hash, or the mediator with its event, and the verifier refuses one whose decider does not fit its verdict and reason, or a release whose decider is not its closing's. An answer call is checked by the mediator before it writes anything: its bytes, its Accord, its signer, the question, the answerer's role for its action, and that the answer's text and salt make its digest. A verifier given the call matches it by its typed hash and checks it again, so the operator cannot claim an answer the call does not say. Rests on receipt-11, maybe-11, maybe-12, verify-3.
- **P17. A verifier needs only the Accord id, and never runs a judge.** It takes the mediator's reference from the founding set whose typed hash is the id it is given, decides each receipt again with the module it trusts and the judgment the receipt claims, and checks that a judge it names is one the Accord let decide; it never fetches anything and never needs a body. Rests on verify-1, verify-2, composition-7.
- **P18. A judge acts only where both sides' terms would ask and list it.** The window asks the core which judges a give would reach, and the core runs the give's own rejection rows and then composition, with no judgment: a judge runs only when the agreed rule of both sides' matching `maybe` terms lists it, with the same judges in the same order on both sides. A give the door or the core refuses, a closed Accord's give and a part the terms pass or block reach no judge. A judge's pass or block decides only with use `decide`; an `advise` judge decides nothing. Rests on composition-5, composition-7, close-3; tests `core/mediator/judges_test.go`, `adapters/local/judge_test.go` (`TestJudgesRunOnlyWhereAsked`, `TestAJudgeOnAClosedAccord`).
- **P19. Every failure of a judge ends at a person.** An error of any kind, no key, an answer below the config's threshold, and a judge still running at the 20-second budget are none, and a give every judge said none of is asked as before. A pass or a block is final. Rests on composition-7, decision record 0023; tests `adapters/judge/run_test.go`, `TestAPassOrBlockIsFinal`, `TestTheBudget`.
- **P20. No judge runs at release, on a part the mediator formed, or on an open question, and a judge never answers.** The window runs judges only before a give is decided; a release, an answer and the passing of time never reach one. Rests on maybe-1, maybe-3, maybe-10, composition-7; test `TestNoJudgeAtRelease`.
- **P21. A request carries the part's kind, its body and the instruction, to the host the window printed, and nothing else.** Besides them it carries the config's model and the key as its credential. Nothing of the message, the envelope, the members, the Accord, a receipt or a salt goes. A raw body is never sent. The adapter speaks HTTPS with verified TLS only, uses no proxy from the environment and follows no redirect, and the host in a config is a DNS name, never an IP literal, a scheme, a path or a user (`config-host`). At start the window prints, for each judge of the card, which kinds may go to which host and model. Rests on decision record 0023; tests `adapters/judge/jev/jev_test.go`, `adapters/judge/config_test.go`, `TestARequestHoldsOnlyKindBodyInstruction`, `TestARawBodyIsNeverSent`, `TestTheWindowSaysWhereContentMayGo`.
- **P22. The judges' key is read once and written nowhere.** The window and the eval read it from `PLACKET_JEV_KEY` when they start, and only the judges' adapters hold it, in memory. No file of the journal, `judged/` included, or of a state directory, no line the window prints, no event and no error text holds it. Rests on `secrets-never-print`, `error-text-no-content`; tests `TestTheKeyIsWrittenNowhere`, `TestTheKeyIsReadOnceAndWrittenNowhere`, `TestTheJudgeNeverPrintsItsKey`.
- **P23. Model output stays out of the evidence and off the screen.** What a judge said goes in `judged/<receipt>.jsonl` only, never in a receipt, an event, a line the window prints or an error. No reader of receipts opens `judged/`, so removing it changes nothing `verify`, `log` or a restart says. Rests on decision record 0023, `claims-stop-at-crossing`; tests `TestTheJudgedFileIsDroppable`, `TestJudgedIsDroppable`, `TestNothingPrintsTheOutput`, `adapters/judge/print_test.go`.

## Judges and prompt injection

A judge reads the part's text, and the part's text is written by the member who gives it. A member who wants a part passed can write text aimed at the judge rather than at the receiver: a note to the reviewer, a claim that the rules changed, or text dressed as the judge's instruction. A model can follow it. Placket cannot tell such text from any other, and does not try to.

What bounds the harm:

- A judge acts only where both sides' terms would already ask a person, and only where both sides list it to `decide` (P18). A part the terms pass or block, a part one side alone lists a judge for, and every part of a kind no `maybe` term names never reach a judge.
- Anything but a clear pass or block at or above the threshold ends at a person (P19), so text that confuses a judge sends the part to a person.
- An `advise` judge decides nothing, so a team can run a judge beside its approvers and compare before it lets the judge decide (`patterns/shadow-judge/`).
- The rule placket's examples keep: no judge is listed to decide on an action that cannot be undone, so a person always answers it. The shadow-judge pattern lists its judge to advise only.
- `evals/judge/` holds synthetic injection cases, and the default config's threshold is the lowest at which none of them passes; when none is, the config ships to advise only.
- Placket runs no command on a judge's say. It passes the part, or holds it.

None of these proves a judge cannot be steered (L23).

## The Jev data flow

For each give a `decide` or `advise` judge of the agreed rule runs on, the window sends one HTTPS request to the host of that judge's config, which in the shadow-judge pattern's config is Jev's API host. The request carries:

- the part's kind;
- the part's body, a text as its text and a data body as its canonical JSON;
- the config's instruction and model;
- the user's own key, as the request's bearer credential.

A raw body is never sent. Nothing else of the part, the message, the envelope or the Accord goes. With no key in `PLACKET_JEV_KEY`, nothing is sent and the judge says none. The reply is read up to 64 KiB, and the window keeps its verdict and score in `judged/`. Jev returns no text of the model's, so a Jev record holds no output.

What Jev keeps of a request, and for how long, is set by Jev's terms for the user's account, not by placket, and placket claims nothing of it (L25). The window prints at start which kinds may go to which host, so the user knows what may leave the machine before a byte does.

## Assumptions

The properties above hold only while these hold. Placket does not check them.

- Ed25519 and SHA-256 are secure as RFC 8032 and FIPS 180-4 define them.
- Each key holder keeps its key secret. Key files are plain hex seeds of mode 0600, written atomically and refused on load when others can reach them (`adapters/keyfile/keyfile.go`).
- A verifier gets the mediator's reference, or the Accord's id, out of band, never from the journal it checks.
- The operating system enforces file modes, unix socket permissions and `flock`, and `fsync` means the data is on disk.
- A torn write leaves a prefix of what was written; limit L10 says what follows when it does not.
- The binary's salt and nonce source, `crypto/rand`, is unpredictable (`cmd/placket/main.go`).
- The door's clock is roughly right. Nothing checks it (limit L3).
- Parties who want to check a journal keep their own state directories and run `placket reconcile`.
- Principals bind only actors they mean to, and the policy lists only principals the parties accept.

## Non-goals

Placket does not try to give these, and no receipt claims them.

- **What a receiver does with content after receipt.** Placket makes no claim about it. See [What a receipt claims](../../README.md#what-a-receipt-claims) and its scope line.
- **The honesty of the mediator or the truth of its clock.** The same section of `README.md` says what a receipt does not show.
- **Confidentiality from the window's operator.** The operator's process holds every part in clear and signs every receipt.
- **Hiding metadata.** Anyone holding the journal reads who gave what kind to whom, when, and with what verdict (receipt-3).
- **Encryption at rest.** Not in this version (decision record 0011).
- **Availability against the local user**, and service across a network: v1 is one process on one machine.
- **Revoking a key or a role inside an Accord.** A new Accord is founded instead (limit L2).
- **Who was at a key.** A signature shows the key, not the person.

## Known limits accepted for v1

Each limit below holds of today's text and code. A change that removes one also removes its entry here.

- **L1. Sizes.** The text bounds nesting depth, label length and timeouts, but not the size of a body, a term list, a founding set or a journal. The door refuses a call over 1 MiB (`MaxCall`, `adapters/local/call.go`), and a client reads no reply over 4 MiB (`MaxReply`), which the window keeps to: the questions reply leaves a question out, and says `more`, where the whole would not fit. Nothing limits how many parts a member gives, how many questions stay open or how many deliveries wait in `held/`, so a member can fill memory or disk. The window reads its own journal whole at start. A journal handed to `verify`, `log` or `reconcile`, and a state directory's files, are read only when they are regular files, each line capped at 4 MiB; the file as a whole is not capped, since a journal grows for as long as its Accord runs. Every other file named on the command line (a founding set's files, a declaration's terms, a part given or changed from a file, a released or shown file) is read whole, with no regular-file check and no cap: the user chose it, and a FIFO there waits and an oversized file fills memory.
- **L2. Bindings are checked at founding only.** A binding's `until` is compared with the founding time and never again (setup-contract-2). A reload founds at the recorded founding time (decision record 0008), so a role outlives its binding for the life of the Accord. Withdrawing a role or a key means founding a new Accord.
- **L3. Time is not checked to move forward.** The door takes the wall clock. Neither the mediator nor the verifier requires a receipt's `at` to be at or after the one before it (receipt-10, receipt-6), so a clock set back writes receipts that go back in time, and moves the staleness and nonce windows with it.
- **L4. Nonces live in memory.** After a restart the door has forgotten every nonce, so a captured call can be sent again within its 60 seconds (decision record 0010). A repeated give is still refused by its envelope's `seq` (crossing-4), and a repeated answer finds no open question (maybe-7); a repeated `get` or `questions` is answered to whoever sent it.
- **L5. The socket trusts the window's user.** The window binds the socket in a directory of mode 0700 it makes beside the path, sets it to mode 0600, and only then links it to the path, so no other user can connect before its mode is set; and the client calls only a socket its own user owns; a call is admitted by its signature, not by who could connect. Any process of that user, or root, can connect, and can read that user's key files, journal and state directories.
- **L6. Parts at rest are in clear.** An unfetched delivery, a released proposal or a changed version included, lies in clear in the journal's `held/` until it is fetched, with the answer call inside it (decision record 0011). The journal's `answers.jsonl` holds every accepted answer call, which names its question and its digest but not its text or salt. A party's `kept.jsonl` and `salts.jsonl` are in clear too. Encryption at rest is later work.
- **L7. A torn answer can lose its release.** An answer's receipts go to disk in one write, after the held files it queued. If a crash cuts that write after the answer's line, the start removes the cut release line and its held file, so an accepted proposal stays unreleased. The log shows the answer with no release time, and the proposer gives the part again.
- **L8. The journal holds answer calls, never their text or salt.** It keeps every call it accepted in `answers.jsonl`, appended and synced before the receipts of its closing, so `verify` on the operator's journal can say an answer is witnessed. A call line with no receipt, after a crash between the two writes, is counted by `verify` and is evidence of nothing; a closing whose call line is missing reads as unwitnessed. The operator can drop the file: an answer is then unwitnessed, never a failure, and a party that fetched a delivery holds the call inside it (decision record 0021).
- **L17. A judge's outcome is the mediator's word.** The window runs the judge, and a receipt a judge decided names the judge by its card name; a verifier checks that the Accord let that judge decide, not what it said, and never runs it again. A judge's own output is not evidence in any receipt (composition-7, verify-2).
- **L18. Completeness only against a close.** A journal cut after any receipt still verifies and conforms; until an Accord is closed, nothing says the journal is whole (verify-4, P3). A whole journal that ends in its close is complete against that close: the close pins the last receipt of every chain, and each chain links back by `prev` (close-4), so the close fixes each chain's receipts and their order within the chain. It does not fix the order of receipts of different chains: whoever holds the journal can move a line before or after a line of another chain, outside the closings that end it, and the journal still verifies and is still complete. The journal order across chains, such as which question an answer follows, is the mediator's word. A subset is never complete, and the close does not say the mediator signed no other journal for the Accord (L19).
- **L19. A stolen mediator key still signs for the old Accord.** Closing an Accord and founding a successor with `supersedes` retires the key for new work (`docs/guides/rotation.md`), but whoever holds the old key can still sign single receipts for the old Accord, which verify on their own, and a whole other journal for it, with another close. Against a close a successor pins, only the receipts that close pins are complete, each chain's in its order, though not their order across chains (L18): `placket verify --superseded-by` refuses a journal whose close is not the one the successor's `supersedes` names. A receipt shown alone, outside a journal checked against the pinned close, proves nothing about completeness. Countersigned closes and outside witnessing of chain heads are later work.
- **L20. A close of an Accord with no receipts founds at the close's time.** The close is then the first receipt, and conformance founds the set at its `at` (verify-1), so a binding whose `until` passed before the close fails `founding`, though the Accord was sound while it ran. This is accepted, not worked around.
- **L21. A close shows every member the shape of the whole Accord.** Once an Accord is closed, every member's `get` and `questions` reply carries the close receipt (close-3), which names every pair of the Accord with its last `seq`, so how many receipts each chain holds, and every delivery not yet fetched, by its receiver and the receipt that queued it (close-2). A member thus learns this metadata of chains it is no party to, which before the close only whoever holds the journal read (non-goals). This is the close's design, and it is accepted.
- **L22. A close too big for one reply is not written.** Every reply that carries the close, and every journal and state-directory line that keeps it, holds it whole, so the window writes no close whose receipt, beside an empty list of questions, would pass `MaxReply` (L1): `placket window close` writes nothing and is tool error `journal`, `receipts.jsonl`, `close-size`. The receipt grows with every chain and every delivery not yet fetched, about 11,000 entries in all at 4 MiB. Once members fetch what is queued for them the close can run again, so in that case the close waits on fetches; an Accord whose chains alone pass the bound cannot be closed. The bound is the implementation's, not the protocol's, and an open Accord refuses nothing for its size (decision record 0022).
- **L23. A judge's pass is a model's.** Text inside a part can steer a judge into passing it where the terms let it decide. The terms, the examples' rule that an action that cannot be undone is always asked, and the eval bound this; they do not prevent it ("Judges and prompt injection").
- **L24. Model output lies in clear in `judged/`.** It may quote the body. It stays in the journal directory until someone removes it, which may be done at any time.
- **L25. What a judge provider keeps is the provider's terms.** Placket says what it sends and where (P21), not what the provider does with it.
- **L26. A judged receipt can come before an earlier `at`.** A judged give's receipt is written when its judges settle, at the time the give arrived, so a receipt of a give decided meanwhile can come before it with a later `at` (L3).
- **L27. Advise runs are not capped per caller.** Each give whose rule lists an `advise` judge starts one outbound request, bounded by the budget. A member's flood of gives starts a flood of requests. A later version may cap them.
- **L28. A short deadline can open a question already past it.** A question's deadline counts from the give's arrival, so a rule's timeout shorter than the judges' budget can open a question past its deadline, which the next tick closes as `timeout`.
- **L29. Parked calls are not capped.** A `questions`, `get` or `result` that waits holds its connection and a goroutine of the window for up to 60 seconds, and the window keeps no count of how many a process parks. A local process of the window's user can open many at once and hold file descriptors; the accept loop backs off when they run out (L1, L5).
- **L30. The labels config is trusted as the user's.** Placket checks the shape of `mediators.json` and that no two entries collide, not who wrote it or what its paths hold beyond that: an entry can name any key file the user can read, and `placket mcp`'s refusal of an answering key reads the founding set the entry names, which is checked against the entry's Accord id. `--allow-answering` lifts the refusal. A label is a local name and is in no receipt.
- **L31. A cursor is good for one start.** The window mints each questions reply's cursor from a random value drawn at its start, so a cursor from before a restart is taken for none and every open question is shown again; `placket watch` keeps no state between runs and prints the questions still open again after a restart.
- **L9. A crash during a fetch can lose a delivery.** The door removes the held file, synced, before it replies. A crash between the two loses that delivery; for a released proposal or a changed version it is the receiver's only copy. The pass receipt stands, reconciliation lists it as unrecorded (receipt-7), and the proposer gives again.
- **L10. The journal repair assumes a torn write leaves a prefix.** At start, only a last line with no line feed is removed (`adapters/journal/journal.go`). A crash that leaves other bytes, or a partial line ending in a line feed, is refused with tool error `journal`, and the window does not start until a person repairs the file.
- **L11. A journal shortened at a line boundary still reloads.** Reload rebuilds each sender's highest `seq` from the receipts left (decision record 0008), so a cut lets an old envelope be accepted again and lets a chain fork from the cut. A party's kept receipts expose the fork as removed (receipt-7). Two questions can then share one echoed envelope; each answer and release belongs to the latest question before it with that envelope, in journal order (receipt-6).
- **L12. A question open at a stop is lost.** Its held part was never written down, so a restart closes it `undeliverable` or `timeout` (decision record 0008, maybe-4, maybe-5), and the asker gives again.
- **L13. Declarations and bindings name no Accord.** A declaration signs only its actor and terms, and a binding names a mediator, not an Accord (setup-contract-1, setup-contract-2). Anyone who holds them can put them in another founding set. That set has its own Accord id. The door refuses a call that names another Accord, and the client refuses a reply whose receipt names one (decision record 0010, `adapters/local/reply.go`).
- **L14. Directory modes are set, not checked.** The journal and state directories get mode 0700 and their files 0600 when placket makes them, but a directory that already exists keeps its mode (`adapters/journal/journal.go`, `adapters/state/state.go`). A key file is checked when it is loaded: one that others can read or write, or that another user owns, is refused with `key-mode` (`adapters/keyfile/keyfile.go`).
- **L15. The card names a module; it does not prove one ran.** Founding reads the card's kernel version and hash for shape only (setup-contract-4). The window refuses a card that names another module than its own build, but `placket founding` and `placket verify` only print a line (`README.md`, decision record 0012). A receipt's card hash is the operator's statement of the module.
- **L16. An answerer sees a question only once it fits the reply.** The door shows each open question to its answerers whole, its body in every form, raw included, with its salt and its ask's receipt, and `placket` checks the body against the receipt before it signs an answer; what `placket questions` prints for a raw part is still its kind and size. Where the questions reply would pass `MaxReply`, the oldest questions come first and the reply says `more`; a later question is shown after earlier ones close, or to a call after the reply's cursor (L1, decision records 0021 and 0024). `placket` does not check the window's key: the window is local, and the Accord id pins the founding set.
