# 0012. The mediator API, placket mcp and the command line

Status: accepted. Date: 2026-11-23.

## Context

An agent reaches a tool through MCP, and a person who answers questions should hear of one when it opens. The command line alone is one process per call, one mediator per command, and a party that learns of a question only by asking for the open questions again and again. A client in any language needs the door's calls written down from the code, in a form a test holds to it, and the code that signs calls, keeps the seq and the state lock and checks every reply needs to be usable outside the command line.

A person trying placket should reach a founded Accord and a verified receipt without learning twenty founding commands first, and every command should say what it takes and fail only where the docs lead a person to expect it.

## Decision

### The mediator API is the door's calls, written as schemas

- The door's calls, `give`, `get`, `questions`, `resolve`, `result`, `view` and `accept`, and their replies, are the mediator API, versioned with the release. They are door formats, outside the freeze: the answer call a resolve carries, and the receipts, deliveries and close a reply carries, are frozen formats of `spec/`, and the schemas describe them as opaque objects, as the door carries them, rather than restate them.
- `api/` holds the schemas, the one source of the door formats, written from the code; `adapters/local`'s package comment points to them. They come in two layers:
  - **the wire layer**, `api/wire/<op>.call.json` and `<op>.reply.json`, with `api/wire/common.json` for the pieces they share, for a client in any language;
  - **the request layer**, `api/request/<op>.json`, what `adapters/client` and the MCP tools take: a give takes the message's receiver, kind, body and its `re` and `topic`, and the client builds the message, mints its id and salt and signs the envelope at its seq; a resolve takes the question, the action and, for an accept or a change, the answer, and the client mints the answer's salt. `cancel.json` is a resolve with action `cancelled`, the asker's; `mediators.json` is the listing tool's input, and no door call.
- `api/config/mediators.json` is the labels config's schema. Every `$id` is `https://placket.tech/api/0.1/<path>`, and no schema names one outside `api/`. They use only the keywords `core/conformance`'s validator compiles. `api` is a Go package that embeds them (`api.FS`, `api.Request`) for `placket mcp`'s tool input schemas, and imports nothing of placket.
- **Worked calls and recorded replies.** `api/internal/gen` writes `api/testdata/worked/`: a founding set of fixed keys, and one worked signed call per op, each fixing the key, the clock and the nonce, a give's message id, salt and seq, a resolve's answer salt and nested signature, with the expected canonical bytes and signature. It uses the standard library alone, so the expected values never come from the code they test, and chooses its inputs (ASCII strings with no `<`, `>` or `&`, whole numbers) so that `encoding/json`'s sorted encoding, HTML escaping off, is the canonical form. `api/gen` writes `docs/reference/mediator-api.md` from both layers, the config schema and the error table. `api`'s tests send the worked calls to a window, record its replies in `api/testdata/replies/`, and fail when either generated directory or page differs from a fresh run. `core/conformance` validates the worked calls, the recorded replies and the config fixtures by path (`TestAPISchemas`), as it reads `spec/` and `vectors/`, so the core gains no exported name and neither module imports the other's code. The worked calls live outside `vectors/`, whose runner and checks are about protocol operations, not door calls.

### Waiting, at the door

- `questions`, `get` and `result` take an optional `wait`, whole seconds from 0 to 60; anything else is `bad-call`. The window parks a call that waits and has nothing to return; its one loop looks at every parked call again after each call it handles, each tick and each judge's result, and answers it when it has something, or when its wait ends, with the reply it would give at that moment (`one-mediator-goroutine`). The connection's goroutine only carries the reply. The door's base deadline, 30 seconds, is the window's `Deadline`; a connection whose call waits may stay open for its wait plus 10 seconds when that is longer, and a client's zero timeout becomes the larger of a minute and its wait plus 15 seconds. A give has no wait.
- **A `get` that waits never takes a delivery.** It replies `{"ok":true,"queued":true}` once one is queued for the caller, and the client then makes an ordinary `get`, which takes it. So a client that hangs up while it waits loses nothing. The window counts the deliveries held for each member to know this without taking one.
- **The cursor.** Every `questions` reply carries `cursor`, the position, in the order the window journaled the asks, of the last question the reply carries, sealed as one AES block (`crypto/aes`) under a key drawn at each start from `Window.CursorRand`: the position's eight bytes and eight zero bytes, which the window checks when it reads a cursor back. So a cursor is opaque to every caller, and the window keeps no table of the cursors it minted. Under `more` the position is the last question kept. A reply that carries none hands back the `after` it was given, so passing it back still asks for what opens after the last question this caller was shown. `questions` with `after` a cursor of this start's returns only the questions opened after it; any other `after`, one from before a restart or one no window minted, is taken for none. So a caller that has seen every open question waits instead of asking again. The window keeps the position of each open ask, and drops those of closed ones.

### The client

- `adapters/client` is the command line's client, a package of its own: it reads the key file, signs every call, owns the seq (crossing-4) and the state lock in the command line's state directory, persists a fetched delivery before it returns it, and checks every reply. Every call takes a `context.Context`, which closes the connection when it ends (`local.Client.CallContext`). The command line's socket commands call it, and print a client error's code as it is.
- **The state lock** (`state-lock`). Only `give` and `resolve` hold it, from before they read the seq until the reply is handled. `questions` reads no seq and writes nothing, so it holds none. `get` and `result` wait without it, then take it to fetch and persist. `give --wait` lets it go before it waits. A call that waits holds no lock, so `placket watch`, or an agent's `result` with a wait, never stops the same key's `answer` or `give`.

### Several mediators, by label

- The labels config is `mediators.json` in placket's config directory, `$XDG_CONFIG_HOME/placket`, else `~/.config/placket`. Each entry names an Accord id, a key file, the founding set's path, an optional socket and an optional label, a local name that is never signed: 1 to 63 of `a-z`, `0-9` and `-`, starting with a letter or a digit, so it is safe in a shell and never looks like an Accord id. Relative paths are under the config directory, and paths are compared cleaned. An entry's state directory is the command line's. `placket mediators` lists it; every socket command takes `--label` in place of `--key`, `--socket` and `--accord`, naming an entry by its label or, with none, its Accord id.
- Each mediator stands alone: nothing about one, its actors, keys, roles or terms, is checked against another's. The one check across entries is local, so mediators on one machine never collide: after the schema (`bad-config`), in this order, two entries with one label (`label-taken`), two of different Accords on one socket, two on one state directory, and two unlabelled entries of one Accord (`mediator-collision`), the first pair by its first index, then its second (`check-order`). A config that fails any is not used at all.
- **A window's defaults.** A window with no `--socket` listens on `<runtime>/<the first 12 hex digits of the Accord id>.sock`, `<runtime>` being `$XDG_RUNTIME_DIR/placket` or else `$TMPDIR/placket-<uid>`, made mode 0700 and checked to be the user's own. Twelve digits keep the path within macOS's 103 bytes under a long `TMPDIR`; two Accords whose ids share them are caught by the labels config, and one takes its own socket. A window given `--socket` that is its Accord's default socket makes the socket's directory too, since the runtime directory may be gone after a restart of the system. With no `--journal` a window writes to `$XDG_STATE_HOME/placket/<the whole id's hex>/`, else `~/.local/state/placket/<hex>/`. An `XDG_CONFIG_HOME`, `XDG_RUNTIME_DIR`, `XDG_STATE_HOME`, `HOME` or `TMPDIR` that is not an absolute path is taken as unset, so no default lands under whatever directory a command was started in.

### placket mcp and placket watch

- **`placket mcp`** is a hand-written MCP server on standard input and output, on the standard library: JSON-RPC 2.0, one message per line, protocol version `2025-06-18`, tools only. It is one party's client. Its tools are `give`, `get`, `questions` and `result`, one per call it lists, each its request plus `mediator`; `cancel`, the asker's withdrawal of its own question, which always sends action `cancelled`; and `mediators`, the listing. `resolve` is never listed, and neither are `view` and `accept`: `placket mcp` never accepts, changes or declines, never runs a command and never holds a mediator's key. Each tool call runs on a goroutine of its own, with a client of its own, so a call that waits never holds another back. `give` returns at once with the question's id when the part is asked about; the agent follows with `result` and its wait.
- **What it serves.** It serves only the labels it is started with, each with its own key, and reads nothing of a label it is not given. It holds proposing keys only, judged by the party's own accepted view: a label whose accepted view has an `answers` row, or an asked row whose `to` names one of its roles, is refused, `answering-key`, unless it is started with `--allow-answering`. A label with no accepted view, whose founding set cannot be read or does not found, or whose kept acceptance is not signed by its key for this Accord, by founding's rows 19 and 20, which any party runs with no opening, is refused, `founding`. The other labels are served as usual.
- **`placket watch`** loops over `questions` with the longest wait and the last cursor, on one or more labels, and prints each new question once, with its label, kind, asker and deadline, and the `placket answer`, `change` and `decline` lines that answer it. It never answers. With `--json` it prints one object per question, as it opens, and its object last: the one exception to commands-1's single object, since it prints for as long as it runs. `patterns/notifier/` runs a command for each.

### One sentence per code

Every code `placket mcp` can return, and every code the command line prints, has one sentence of cause and fix in `adapters/errtext`, which imports nothing of placket. A row is keyed by where its code comes from: a code in a door reply by its member (`door`, `rejection`, `error`); every other by the package that declares its `Code` type (`adapters/client`, `adapters/mcp`, `adapters/state`, `adapters/keyfile`, `adapters/local`). The command line's own codes have rows under `adapters/cli`, and the journal's under `adapters/journal`; a code the command line prints from another package's `Code` type keeps that package's one row, and one only spelled like a code of `placket mcp`, such as `founding`, has a row of its own. The same spelling under two keys has two sentences. A tool error's text is `<code>: <sentence>`. The command line prints only the code: the sentences are in `docs/reference/cli.md`, whose Errors section `adapters/cli/gen` writes from these rows, as the mediator API's Errors section lists every row but those two keys'. Two kinds of code that follow another have no row: the verifier's code after `error verify`, which the protocol defines (verify-1), and a judge config's code after `error judge` (record 0009). `adapters/mcp`'s codes are `answering-key`, `founding`, `bad-arguments` (arguments that fail the tool's input schema or the 60-second cap) and `internal`, a failure no other code names; malformed JSON-RPC is answered with JSON-RPC's own codes.

### The command table

`adapters/cli` keeps one declarative table of its commands and subcommands (`table.go`), and each command reads its flags from its row. `adapters/cli/gen` writes `docs/reference/cli.md` from it, and `adapters/cli`'s tests fail when the page differs from a fresh `go run ./adapters/cli/gen`.

### `--help`

- `--help`, `-help` or `-h`, given as a flag and not as a flag's value, asks for the command's usage; it is carved out of commands-1's rule that a flag that cannot be read is the error `usage`. The command prints its usage on standard output: `usage: placket <command> [flags]`, one line per flag it reads, in name order, each starting `--<name>` with the flag's kind, its usage and any default that is not the zero value, and then one line per subcommand, `placket <subcommand> [flags]`. Standard error is empty, and the exit is 0. It reads no file, socket or state, and checks no flag the command requires.
- With `--json` it prints one object: `command`, `exit` 0, `flags`, a list of `{"default","name","usage"}` in name order, and `subcommands` when there are any. `placket --help` prints the usage line and one line per command, or with `--json` `{"commands":[...],"exit":0}`. `mcp --help` prints its usage like any command; `mcp --help --json` is refused as `mcp --json` is, `{"error":"usage","exit":3}`, since `mcp`'s standard output carries the MCP protocol.
- `key --help` names `key new` and `key ref`, `window --help` names `window close`, and `init --help` names one `init <example>` per example; `key new --help`, `window close --help` and `init approve --help` print that subcommand's flags. `--help` given as a flag's value is that value. `placket` alone and a command that does not exist stay the error `usage`, exit 3.
- The usage text is built from the command table's rows, so it cannot list a flag the command does not read, and it is the text `docs/reference/cli.md` gives.

### `--json`

When a command's flags cannot be read, `--json` still turns on the object in every spelling a boolean flag reads as true, `1`, `t`, `T`, `true`, `TRUE` and `True`, and the last such flag before `--` decides. `deliveries` is present, `[]` when empty, wherever `fetched` is.

### Answers to a question the window does not show

- `asked` means only that the part the window shows is not the one its ask's receipt names: the receipt is not the question's, not under this Accord, not of the kind shown, or the body under the salt does not make its digest. Nothing is signed or sent.
- A question the window does not show, on any page of its `questions`, is not `asked`. `answer`, `change` and `decline` sign the answer call and send it, and print the mediator's refusal as any refusal prints: `rejected no-open-question` for a question already closed, `rejected not-an-answerer` for a key that does not answer it, exit 2. A decline's comment is given only after the window takes the decline, so a refused decline gives none. This is safe: a question the window does not show cannot be answered, the mediator refuses the call, and the signed call is never part of a receipt.
- Before it decides the window does not show a question, the client reads every page: while a reply says `more`, it asks again after the reply's cursor. One question always fits in a reply, so every open question is on some page.
- A closed Accord is still the rejection `closed` before anything is signed, and `placket questions` still leaves out a misstated part and ends in `asked`.

### A fetched body is never lost

- A body the door has handed over is no longer queued, so the command line keeps it rather than lose it. A body `get` cannot write to standard output is kept in `kept.jsonl`, unless `--keep` or `--all` kept it already, and `get` ends in `error file kept`, exit 3, as it does for a body it could not write under `--out`. With `--all` it stops at the first body it cannot write. The binary ignores SIGPIPE, so a write to a closed pipe is an error `get` acts on, not a signal that kills the process.
- With `--json`, the object goes to standard output after the command's work. When it holds a body and cannot be written, `get` keeps each body it holds that it had not kept, and ends in `error file kept`, exit 3.
- A delivery whose record in the state directory fails after the door handed it over is still handed over: `client.Get` returns the delivery with the state directory's error, and `get` writes the body as it would, then prints the error. The order of the records is unchanged, and the ones after the failure are not written. A caller of `client.Get` handles the delivery before the error.

### Smaller rules

- `state.Error` has `Detail`, and `state.DetailTooLarge`, `too-large`, is its one value: an `actor` or `seq` file over its 4 KiB limit is `error state actor too-large`.
- `local.Run`, for a window started proposed, refuses with setup's `opening-missing` before it listens when it does not hold every member's opening (setup-contract-13), as founding does once acceptances are given.

### `placket init`

- `placket init <example> [--dir D] [--label L]` founds one example Accord, or two, for one person, in one command. `approve` is approve before apply: the parties `agent`, `person` and `applier` hold the roles `agent`, `decider` and `applier`; the agent's `proposal` to the applier is asked of `decider`, the person accepts, changes or declines it, and the applier is handed what was released. `merge` is an out-gate on a merge, with the same parties and roles; the agent's `merge`, data naming a pull request, is asked of `decider`, and the applier merges what was released. `handoff` is handoffs between agents across two mediators: the Accord `<label>-plan` has `planner` and `coder`, and the planner's `plan` passes to the coder by the terms; the Accord `<label>-review` has `coder` and `reviewer`, and the coder's `work` passes to the reviewer. Nobody is asked. The label is the example's name unless `--label` gives one. The person's key is a party key holding `decider`; the principal's key only grants roles.
- **What it writes.** Everything goes in D, by default `<placket config dir>/<label>/`, made mode 0700. A D that holds anything is refused with `dir-not-empty`, before anything is written. In D: the keys `mediator.key`, `operator.key` and `principal.key`, and one key per party and Accord, `<entry>.key`, each mode 0600 (`keys-on-disk`), the coder of `handoff` holding one key in each Accord; each party's opening, `<actor hex>.opening.json`, so D is the window's `--openings`; for each Accord a directory of its label, holding each party's terms file, `<party>.terms`, the policy, the mediator file, the card, `founding.json` and `acceptances.json`, and the window's `journal/`; and for each party its view and its acceptance in its state directory, as `placket view` and `placket accept` keep them. It seals each party's declaration under a salt it mints, founds the set with every opening, builds each member's view and signs that member's acceptance with its key, and founds again with the acceptances, so the window starts founded.
- It adds one entry per party key to the labels config, named `<accord label>-<party>`, such as `approve-agent`, each with the Accord's default socket written out. A label taken already in the config is `label-taken`, and a label whose longest entry name would be over 63 characters is `usage`, as is the label `applier` for `approve` and `merge`, whose Accord's directory would be `D/applier/`, where the applier is fetched; each before anything is written. A failure after D is made removes what it wrote.
- **What it prints.** For each Accord, its id, each party's label, key reference and role, and the window's command line in full, with `--socket` and `--journal`. Then the `claude mcp add` line that serves the agents' labels, and, for `approve` and `merge`, the `placket watch` line of the person's label and the lines that fetch the example's applier from the repository into `D/applier/` and run it. The applier is fetched at the binary's version tag, pinned to the tag's commit when the build carries it, since a tag can be moved and a commit cannot; a build with no version tag fetches it from `main`, and says so. Nothing checks the file fetched against a checksum: the guides say to read it before running it. `init` does not start the window.
- **The example appliers** are patterns, outside the requirement text, run by `make ci`: `patterns/local-apply/` is `approve`'s, and `patterns/github-merge/` is `merge`'s.
- **The first hour.** `tests/test_first_hour.sh` runs each example from a clean `HOME`, as a person would: it builds the host's archive as `.goreleaser.yaml` builds it, from the tree, unpacks it and puts its `placket` first on `PATH`, runs `placket init`, starts each window with its printed line, gives through `placket mcp` as Claude Code would, answers with the line `placket watch` prints, runs the applier as the fetch line places it, and runs `placket verify` with every opening on each journal. An entry passes when verify prints its `valid` and `conforms` lines, within 60 seconds. The three run side by side. `tests/firsthour/` is a package of the root module, a `main` the test builds: a scripted MCP client that starts the command the `claude mcp add` line names, speaks to it over standard input and output, and makes the tool calls a script lists. It is not Claude Code and runs no model.
- `init` holds every key in one directory, so it is for one person trying placket. An Accord between parties who do not share a machine is founded with the founding commands, each party sealing its own terms and accepting its own view.

## Consequences

- An agent reaches several mediators through one `placket mcp`, each with its own key, and a person hears of a question when it opens.
- A client in any language has schemas, worked calls and a reference to build on, and a change to the door's formats fails a test until they are updated.
- A parked call holds a connection and a goroutine for up to a minute. Nothing caps how many a local process opens (threat model, L29).
- The labels config is trusted as the user's own file: placket checks its shape and that its entries do not collide, not who wrote it. A config that names another founding set than the window's is refused only when the set's id is not the entry's Accord.
- A person reaches a founded Accord in one command, and a verified receipt from the lines it prints. The agent learns the receiver's key reference from what `init` prints; the MCP tools do not list an Accord's members.
- An answer to a closed question reports `rejected no-open-question`, exit 2, the code `give --wait` and `result` report for such a question.
- `get` may exit 3 with `error file kept` where it would otherwise have lost a body, and may exit 3 with the state directory's error after printing the body.
