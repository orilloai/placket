# 0011. The door, the journal and the state directory

Status: accepted. Date: 2026-11-23.

## Context

A mediator is a value in memory (record 0008). For parties in separate terminals to use it, something must hold it in a running process, take their calls, prove who each caller is, and hand the core exactly what was signed, with the time the core takes as a parameter (`core-no-world`). That is the door, and the process that holds one Accord's mediator behind it is the window. A call must be bound to one caller, one Accord and one moment, so a captured call cannot be sent again later or against another Accord. And the decider must see the part it is asked about.

A window can stop at any moment: a signal, a crash, a kill. What it replied before it stopped must still hold after it starts again: every receipt it returned, every delivery it queued and nobody fetched, and every sequence number it took (`restart-reproducible`). Something must keep the mediator's record on disk, in an order that a crash at any point leaves consistent, and read it back without deciding anything. The receipts on disk are also the evidence a third party verifies and the log is made from (`journal-is-evidence`, `log-from-receipts`). Each party keeps its own record beside it, so that reconciliation can show what a journal left out.

## Decision

### The socket and the call

- **The socket.** A unix socket, mode 0600, one call per connection: the client writes one call and a line feed, reads one reply and a line feed, and closes. A call is at most 1 MiB (`MaxCall`); the door stops reading a longer one and refuses it. A window removes a socket file left at its path only when connecting to it is refused, so a live window's socket is never taken over, and a path that holds anything but a socket is never removed. The client calls only a socket owned by its own user, never through a link, and refuses an outcome whose receipt names another Accord than its own.
- **The call** is `{"call","sig"}`. `call` holds `op`, one of the calls `api/` lists (record 0012), `caller` (the signer's actor reference), `accord` (the Accord id the caller expects), `at` (the caller's clock, whole seconds), `nonce` (16 random bytes in hex) and `args`, by op. A give's message and envelope travel in `args` as standard base64 of the exact bytes the caller signed. `sig` is the call's signature: `signing.SignPayload` over the call's canonical bytes, under the media type `application/vnd.placket.call+json`, defined once in `adapters/local` (`call-signing`). The core refuses its five type URIs as payload types, so a call's signature can never stand for a placket object's, and no type URI is needed for it.
- **The door's checks, in order** (`door-check-order`): size (`too-large`), form (`bad-call`), the signature under `call.caller` (`bad-signature`), the Accord (`wrong-accord`), the time within 60 seconds of the door's clock (`stale`), and the nonce, unseen in the last 120 seconds (`replayed`). The first that fails decides, and the call reaches no mediator function. Only a call that passes all six has its nonce remembered, so a refused call changes nothing, the nonces included. Then a caller's second `give` while its first is with a judge is `judge-busy`, and a window not yet founded refuses every op but `view` and `accept` with `not-founded` (below). Then the mediator runs, and its first row is membership: a stranger's well-signed call is `not-a-member` whatever its message holds.
- **The door's codes are a type of their own,** never a rejection or an error of the core, and the reply carries each under its own member, `door`, `rejection` or `error` (`rejection-vs-error`). Every failure of the door itself, such as its randomness failing, a reply it cannot encode, or an error from the mediator that is neither a `*mediator.Rejection` nor a `*mediator.Error`, is `door-internal` under `door`, never the mediator's `internal`; when even the reply cannot be encoded, the door writes the fixed reply `{"door":"door-internal","ok":false}`. The door repeats none of the core's checks (`adapters-no-recheck`), and hands the core the operation's bytes as decoded, never encoded again (`door-passes-bytes`).
- **The door owns the clock** (`door-owns-clock`). It reads its clock once per call, at whole seconds, and uses that time for the staleness check, for a tick before the operation and for the operation itself; with no call, it ticks once a second. When a give is asked about and the question has no answerers, it finds it undeliverable at once. It mints no salt and asks for no release itself: the answerer does both, in its signed call (record 0009). The clock is a parameter of the window, so a test can drive two windows with one script.
- **One goroutine owns the mediator** (`one-mediator-goroutine`). Each connection is read on a goroutine of its own and handed to the window's one loop over a channel; the loop runs the checks, the tick, the operation and the journal writes, and hands back the reply. Judges run on goroutines the loop owns and hand their results back to it (record 0009). No other goroutine touches the mediator.
- **`judge-busy`.** A caller's second `give` while its first is with a judge is refused with the door code `judge-busy`. Envelope `seq` must rise (crossing-4), so a later give must never reach the core before an earlier one; queuing would hand the core the caller's gives out of order whenever the first is refused. The check is about the order of the caller's calls, never about the operation inside one, so it is the door's code and not a rejection (`adapters-no-recheck`). It runs right after the six checks, the nonce last, so the refused call's nonce is spent and a retry is a new signed call, and before the tick, so the refused give writes nothing. Only a `give` is refused: the busy caller's `get`, `questions`, `result` and `resolve` go on. A party's own command line holds its state lock across a call, so it never meets this.
- **Deadlines.** The connection deadline the door sets is 30 seconds. Before writing a reply, the door sets a fresh write deadline of 5 seconds, so a slow call does not eat the reply's time, and the judges' 20-second budget plus that margin is below the connection deadline.
- **The replies.** No reply carries a salt the door minted. A give or a resolve returns its outcomes, the release's beside the answer's. A get returns the delivery as the core returned it, its answer call inside it, and, once the caller's queue is empty and the Accord is closed, the close (record 0010). `result` returns a closed question's closing and release to its asker.
- **The `questions` reply** carries, for each open question the caller may answer, the ask's receipt, the part's salt and its body in the form it was given, a raw body included, as standard base64. It goes to an answerer of the open question only, which keeps the salt rule of `docs/security/secure-coding.md`. It holds as many whole entries as fit, oldest first, and says `"more":true` when it left some out; a later question shows once earlier ones close.
- **A core read for questions.** `mediator.Question` (record 0008) gives an open question, its part included, to the mediator's own reference and to the question's answerers, and to nobody else. The door uses it twice: as the mediator, to journal an ask's deadline and roles before the ask's receipt, and as the caller, for `questions`. So the door neither matches a term to find who may answer (`one-decision-module`) nor keeps a copy of a held part. For `questions` the door first reads the empty id, which no question has, so the core answers with its membership row: a stranger's `questions` is `not-a-member` from the core, whether or not a question is open, and so is a call signed with the mediator's own key. The door never hands the mediator's own reference to the read for a call, so even a mediator key that were also a member would be shown no question.
- **A held part is shown to its answerers.** maybe-1 says that the held part leaves the mediator only by a release, and that while the question is open it is shown to the question's answerers and to no one else. An answerer asked to accept, change or decline a part must be able to read it: an answer about content nobody showed them would record nothing. The part still crosses to its receiver only by a release, the asker learns nothing new, and a member who is not an answerer, or a stranger, is shown nothing.
- **A reply's size.** `MaxReply` is `4 * MaxCall`. The client reads a reply through a bounded reader and refuses a longer one with its `reply` error. The bound holds one delivery, whose body came in under `MaxCall`, with its receipt and its answer call, with room to spare. The `questions` reply fits it: the window counts every open question first by its size alone, and leaves out any question, with every one after it, that would take the reply past `MaxReply` even so; then, oldest first, a question shows its part while the reply still fits, and is otherwise shown by its size in bytes. A question left out, or shown by its size, is shown in full once older questions close.

### The window

- **A proposed Accord.** `placket window --founding S --openings DIR` with an empty journal starts a proposed Accord: it runs rows 1 to 17 of founding with every opening, and serves only `view`, which returns the caller's own view, and `accept`, which takes the caller's signed acceptance and checks it by rows 19 to 21; an acceptance that fails is refused with that row's founding code. Every other op is refused with the door code `not-founded`. Once every member has accepted, the window founds at that time, writes `acceptances.json` beside the founding set, journals the founding, prints its founding line and serves as before. Started with `--acceptances A`, or with an `acceptances.json` beside the founding set, it is founded at once, on an empty journal as on a founded one; a founded journal with neither is refused `acceptance-missing`.
- **What the window prints.** On start the Accord id, the card hash and the operator, its founding line, and for each judge of the card which kinds may go to which host and model (record 0009); then one line per event, the op, the product word, the reason or code and the receipt's id, and one line per advise judge's run. Never a body, a salt, a seed, a key, a question's part or a judge's output. On SIGINT or SIGTERM it stops and writes nothing; the next start closes what was left open.
- **Nonces live in memory only,** so after a restart a captured call could be sent again within its 60 seconds. The socket is local and its mode limits it to the window's user, so this is accepted for this version.

### The journal

- **The journal is a directory**, mode 0700, that the window locks with an exclusive `flock` on its `accord` file while it runs; a second window on it is `journal-locked`. It holds `accord` (the Accord id, the card hash, the mediator and the founding time, written once), `receipts.jsonl` (each receipt as the mediator returned it, one per line, made empty at the first start just before `accord`, so that a founded journal always has one and a reader can refuse a directory that has none), `questions.jsonl` (each ask's question, deadline and roles, never a byte of its part), `answers.jsonl` (each answer call the window accepted, one canonical call a line, with no text and no salt), `held/` (each delivery not yet fetched, in a file named by its receipt's id, `{"delivery","to"}`, the answer call inside the delivery) and `judged/` (each judged receipt's judge records, which no reader of receipts opens; record 0009). The formats are written in `adapters/journal`'s package comment; they are door formats, not frozen ones.
- **Every write is synced before the reply** (`journal-synced`), in this order. A pass: its held file, then its receipt. An ask: its questions line, from `mediator.Question` under the mediator's reference, then its receipt. An answer: its call's line in `answers.jsonl`, then every held file it queued, then all of its receipts in one write, so that a crash rarely leaves an answer without its release. A tick, a reload's closings or a close: their receipts. A get: the removal of the held file, and the directory synced, before the reply. A write that fails ends the window with the failure and no reply; the next start reloads what the disk holds.
- **A call's line comes before its closing's receipts,** so a line no receipt names, as after a crash between the two writes, is read as evidence by no one: verify counts it, and a closing whose line is missing reads as unwitnessed.
- **Reading is not judging.** At start the journal adapter reads the files and hands `mediator.Reload` what they hold: the receipts in order, the questions lines of the questions still open, and each held delivery. It finds the open questions by `receipts.Releases` over the receipts `receipts.Verify` passed under the mediator's reference, since `questions.jsonl` keeps every ask; when that verification fails, it leaves the open entries as they are, and `Reload` refuses the list. Every check of what was read is Reload's. When Reload refuses, the window stops with tool error `journal`, naming the file and the line, from the index Reload gives, and the core's code; the journal is left as it was, but for the repairs below.
- **The only repairs.** A last line of `receipts.jsonl` with no line feed was never answered, and is the one change ever made to that file: it is removed, with a line on stderr. A last line of `questions.jsonl` or `answers.jsonl` with no line feed was never written either, and is removed, so that the next line appended is whole. These are cut before Reload runs, so a start that Reload then refuses has still cut them. `verify`, `log` and `reconcile` read `receipts.jsonl` without the lock and write nothing: a directory without one is tool error `journal`, and a last line with no line feed is left out with a line on stderr saying the file was cut there. Besides these, two clean-ups: a questions line whose question is in no receipt line is left in the file, not handed on, and noted; a held file whose receipt is in no line never crossed, and is removed, with a line on stderr, once Reload has taken the rest, so that a start that stops changes nothing.

### The state directory

- **A party's state directory**, by default `<key file>.state/<Accord hex>/`, holds `actor`, `lock`, `seq`, `envelopes.jsonl`, `delivered.jsonl`, `kept.jsonl`, `salts.jsonl` (the salt of each delivery fetched, by its receipt's id), `close.json` (record 0010), `view.json` and `acceptance.json` (record 0006). The commands take its lock as record 0012 says (`state-lock`). An envelope's line is written before its call is sent, and removed only when the call is refused, so a submission lost with the window shows as missing. `seq` is written only after a reply, so the next give takes the seq above both `seq` and the highest envelope line: a give the window journaled whose reply was lost never has its seq used again, which the mediator would refuse; the protocol lets a seq skip numbers. A last line of any of its `.jsonl` files with no line feed was never written: reads leave it out, and the lock removes it, with a line on stderr, before anything is appended.
- **Kept parts.** Under `--keep`, and for every delivery a wait fetches, a party writes the part to `kept.jsonl`: a part it gave as its message's exact bytes beside the receipt, and a part it fetched, or a version it gave as an answer, as the delivery holds it, with the answer call inside it. `answer --keep` and `change --keep` keep the answer call the key signed and the salt it minted. A decider's comments are always kept by the decider, since only the giver's copy can show which question a comment was about.
- **Files placket is handed.** `adapters/internal/lines` reads a journal's or a state directory's file only when it is a regular file, with a cap on each line, and `keyfile` opens a key file through it. `adapters/internal/seeds` reads the vectors for the adapters' fuzz tests, which cannot import the core's internal packages.

### The log

- **The log** is made by `adapters/export` from `receipts.jsonl` and any number of state directories. It verifies the receipts first and prints no row when they fail or when `receipts.Releases` refuses them. One row per question, in the order asked; the answer, the times and the release come from receipts alone, through `receipts.Releases`; the topic, the comment and the texts only from kept parts a verified receipt covers, by the envelope's hash for a part given and by the salted digest for a part fetched; `answer_signed` only after a kept answer call verifies and is the call the closing's `by` names, for the row's question and action: an accept or a change signed by the row's answerer, for the digest's text, and a cancel by the asker. For a decline it shows a signed call bound to the closing, not who signed it: a decline's signer is not compared, since any answerer may decline while the closing's `from`, the row's answerer, is the first answerer, and the mediator refused a decline from any member that is not an answerer when it took the call (maybe-6). A kept part no receipt covers is left out with a line on stderr. CSV cells that start a spreadsheet formula are prefixed with `'`.

## Consequences

- An unauthenticated call never reaches the core, and a refused call leaves no trace in the journal.
- A caller can tell the door's own failure from the core's, and a log of replies records them apart. The window sends no reply larger than `MaxReply`, so a client refuses only a reply no window sends.
- The decider sees what it answers about, and nobody else sees a held part. The window itself never prints one.
- An answerer with many large open questions sees some of them by their size alone, or not yet at all, until older ones close.
- A window killed between two calls carries on with the same receipts, chains and sequence numbers; a question open at the kill is closed by one receipt at the next start, and a delivery not yet fetched is fetched once.
- A delivery's body, a released proposal or a changed version included, lies in clear in `held/` until it is fetched, with its answer call. Encryption at rest is not in this version.
- A crash after a held file is removed and before the fetch is answered loses that delivery; its receipt stands, and reconciliation shows it as unrecorded.
- The log adds nothing a receipt did not record: with no state directory it still shows every answer and release.
