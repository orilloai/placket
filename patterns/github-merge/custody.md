# Custody: what GitHub must hold for the applier to be the only way to merge

Placket's receipt says the mediator released a part naming a commit. That the commit could not merge without it is GitHub's to hold, and that no one but the deciding role released it is the window's account's to hold, by the settings below. Follow them in order, for each repository the applier serves, before the agent gets any credential to it.

1. **Give the applier an identity of its own.** Create a GitHub App for it (Settings → Developer settings → GitHub Apps → New GitHub App) and install it on the repository alone (Install App → Only select repositories). Give it these repository permissions and no others: Contents, read and write, to merge; Pull requests, read and write, to read the pull request and comment on it; Commit statuses, read and write; Metadata, read. Where an App cannot be used, and only on a repository an organisation owns, the fallback is a machine user, a GitHub account that is no person's, with a fine-grained token (Settings → Developer settings → Personal access tokens → Fine-grained tokens) limited to this repository and the same permissions, and a team of the organisation that holds that machine user and no one else. On a repository a person owns, the App is the only way: a ruleset's bypass list takes roles, teams, Apps and deploy keys, not a single user. Never use a person's own token: the receipt names a decider, and the merge would then name the person too.

2. **Let the applier merge into the bases it serves, and into no other branch.** Add two branch rulesets (the repository's Settings → Rules → Rulesets → New ruleset → New branch ruleset). Each has Enforcement status: Active, and the rules Restrict updates, so that only the bypass list may update the branch, which is what a merge does; Restrict deletions; and Block force pushes.
   - **The applier's bases.** Target branches: the base branch, or branches, the applier serves and no others, such as Include default branch. Bypass list: the applier's App, or the team that holds only its machine user, and nothing else: no role, no other team, no other App, and not Repository admin.
   - **Every other branch.** Target branches: Include all branches, then Exclude by pattern the applier's bases and the branches the agent pushes to. Deploy and release branches are among those it covers. Bypass list: never the applier, and never the agent; leave it empty, or name only those who update those branches by hand today.

   GitHub's merge call fixes the head commit but not the base, so a pull request's author can change its base between the applier's read and its merge. The second ruleset keeps such a merge out of every branch but the applier's bases: GitHub refuses it, and the applier prints `refused pr N merge`. Among its own bases the applier can still be retargeted: a release into one may merge into another it serves, which it sees only when it reads the pull request again after the merge, and then it stops, posting no comment or status (README.md, "When it stops partway"). Where that matters, give each base an applier identity of its own, with its own ruleset of the first kind.

   Then check it. With the agent's credential, try to merge a pull request into one of the applier's bases, by the web page and by `gh pr merge`: both must be refused. With the applier's credential, try to merge a pull request into a branch outside its bases, such as a release branch: it must be refused. The agent's credential must not hold the Admin role on the repository or own its organisation, since either can edit the rulesets.

3. **Run the window, and keep the deciding role's key, where the agent cannot reach them.** Placket trusts the user who runs `placket window` fully: that user holds the mediator's key, every party's opening, the journal and the socket, and can read every key file of its account (`docs/security/threat-model.md`, L5). An agent that can act as that user, or read the deciding role's key, can release a merge with no person's yes. So run the agent in an account of its own, never the person's own account, and make another account for the window, such as `placket`, that is neither, even where the person and the agent share one machine, and that the agent's account cannot `sudo` or `su` to. Keep the mediator's key, the openings, the journal, the socket and the deciding role's key there, and the agent's own key file too. The person reaches that account only from an account or a machine the agent's account cannot touch, by a login the agent's account cannot use, such as their own password or an SSH key that is not on the agent's account, and answers there with `placket answer`. Whatever runs in an account can watch and change what a login made from it does, so never reach the window's account by `su` or `ssh` from the account the agent runs in, or from any account whose files or processes it can reach.

   The socket is that account's alone: the window makes it mode 0600, and a client calls only a socket its own user owns. So the agent reaches the door through `placket mcp`, run in the window's account under the agent's own label, by SSH with a key that may run that command only. In the window's account's `~/.ssh/authorized_keys`, the agent's public key gets the line `restrict,command="placket mcp --label agent" ssh-ed25519 AAAA… agent`, and the agent's MCP client starts `ssh placket@HOST` as its server. `placket mcp` serves only the labels it is started with, refuses a label whose key answers questions unless it is started with `--allow-answering`, and takes a body inline, never a path, so the agent gives, gets and asks as itself and nothing more.

   Then check it, as the agent's own user, with the agent's own credentials: `id -un` must print the agent's own account, not the person's; `cat` of the mediator's key, an opening, the journal, the deciding role's key and the agent's key file must each be refused, `Permission denied`; `sudo -l` must list nothing that runs as the window's account or as the account the person reaches it from; and writing to that account's home directory or its shell's startup files, or listing its `~/.ssh`, must be refused, where the person reaches the window's account from this machine at all; and `ssh placket@HOST cat mediator.key </dev/null` must print no key, since it runs `placket mcp` instead, which ends at once with nothing on its input.

4. **Run the applier where the agent cannot reach it.** Run `apply.sh` in the window's account, outside any repository or directory the agent can write to. Its `placket get --label` calls the window's socket, which only that account can reach, and it does not speak MCP, so it runs nowhere else. An agent that can edit `apply.sh`, its `applied.jsonl`, its labels config, the founding set file its label names as `founding`, from whose bindings it takes the deciding role's keys, or its state directory, which holds `kept.jsonl` and which `placket mediators` prints, decides what the applier merges: a recovery by hand pipes `kept.jsonl` back into it (README.md, "When it stops partway"). Keep the applier's credential, the App's private key or the machine user's token, and the applier's Placket key file where the agent cannot read them, such as that account's own secret store.

   Give `gh` the applier's identity in `GH_TOKEN`, set in that account's environment for the applier's run only; `gh auth login` signs in a user, never an App. An App's token lasts one hour, so mint one from its private key before each run: a JSON Web Token signed with that key, whose issuer is the App, sent as a bearer token to `POST /app/installations/INSTALLATION_ID/access_tokens`, answers with the installation's token. With `forever` set to `yes`, start the applier again with a new token before the hour is up. A machine user's fine-grained token is `GH_TOKEN` as it is, renewed before the date it expires. When GitHub refuses the credential, HTTP 401, the applier stops, refusing nothing, and README.md, "When it stops partway", says how to go on.

   Check it as in step 3: as the agent's user, writing to each of those files, and reading the credential and the key file, must be refused.

5. **Never rest custody on the status or a required check.** The `placket` commit status is written after the merge, for the auditor to find the receipt; it is not a gate. Do not make it, or any check, the thing that stops an agent's merge: the ruleset of step 2 does that. Anyone who may write statuses can set a status named `placket`, so an auditor trusts a merge only once `placket verify` checks the receipt it names, and the body it releases names that merge (README.md, "The auditor's path").
