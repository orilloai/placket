# Custody: what the applier rests on

The receipt says what the mediator released. That a merge happened only through the applier, and only after a release, rests on the GitHub settings and the accounts below, which Placket neither sets nor checks. Follow every step, in order, for each repository the applier serves.

1. **Give the applier an identity of its own.** Make a GitHub App (Settings, Developer settings, GitHub Apps, New GitHub App) with only these repository permissions: Contents, read and write, to merge; Pull requests, read and write, to read a pull request and comment on it; Commit statuses, read and write. Install it on this repository alone. Whether the App also needs the Workflows permission to merge a pull request that changes `.github/workflows/` is not known: GitHub's documentation lists the merge call under Contents and says nothing of a merge that touches a workflow file. Grant Workflows only if such a merge is refused without it, since it also lets the App write workflow files. If an App is not possible, use a machine user of its own with a fine-grained personal access token with the same permissions on this repository alone; this works only in an organisation, since step 2 needs a team. Never use a person's own token, and never the agent's.

2. **Let only the applier merge.** In the repository's Settings, Rules, Rulesets, make a branch ruleset, its enforcement Active, that targets the one base branch the applier serves, with "Restrict creations", "Restrict updates", "Restrict deletions" and "Block force pushes". Its bypass list holds the applier's App, set to Always, and nothing else: no repository role, no team and no person. For a machine user, the bypass list holds a team whose one member is the machine user. One applier identity serves one base branch: GitHub's merge call fixes the head commit and not the base, so a pull request retargeted between the applier's read and its merge call merges wherever the ruleset lets the applier merge (threat model, L36). For another base branch, use another App with rulesets of its own. Then make a second ruleset, Active, that targets every other branch, with "Restrict updates" and the applier off its bypass list, so that a pull request retargeted after the applier's read cannot merge there; whoever pushes to those branches, the agent included, goes on its bypass list. The agent may sit only on the second ruleset's bypass list, never on the first's. The agent's own GitHub credential has no admin role on the repository or the organisation, so it cannot change a ruleset.

3. **Keep the window, the deciding key and the applier from the agent.** Run the agent in an operating system account of its own. Run the window, with the mediator's key, the openings, the journal and the socket, and keep the deciding role's key, in another account, which the agent's account cannot read, write or log in to. Placket trusts the window's account fully: it holds the mediator's key and can read every key file it holds (threat model, L5), so the agent must never run code there. The person who answers logs in to that account from a machine the agent's account cannot touch. The agent reaches the door through `placket mcp`, run in the window's account behind a forced command, such as an SSH key in that account's `authorized_keys` with `restrict,command="placket mcp --label agent"`, so that the key runs nothing else and gets no forwarding and no terminal.

4. **Run the applier in the window's account, outside any repository the agent can write to, with a credential the agent cannot read.** `apply.sh` calls `placket get --label`, which reaches the window's socket, so it runs in the window's account. Keep its copy of `apply.sh`, `applied.jsonl`, the labels config, the founding set file that config names, the applier's key and its state directory there, in no checkout of a repository the agent can push to, so the agent cannot change what the applier runs or which keys it takes for the deciding role's. Keep the App's private key, or the machine user's token, readable by that account alone. `gh` reads its token from `GH_TOKEN`: an App's installation token is minted from the App's private key and lasts one hour, so mint one before each run (a JWT signed with the private key, exchanged at `POST /app/installations/INSTALLATION/access_tokens`) and export it as `GH_TOKEN`. When it lapses, the applier stops at the next call GitHub refuses with 401, and says so.

5. **Never rest custody on a status or a required check.** Do not make the `placket` status a required status check, and do not let any ruleset or workflow take it as leave to merge. Anyone who may write statuses can set one named `placket`; it is for the auditor, who checks the receipt it names with `verify`. The ruleset of step 2 is the gate.

6. **Check it, with the agent's own credential.** As the agent's account, with the agent's GitHub token: open a throwaway pull request made for the check, never a real one, whose one commit is empty, and `gh api -X PUT repos/OWNER/NAME/pulls/N/merge` on it must be refused; `git push` of an empty commit made for the check, on the tip of a base branch, to that branch must be refused; so that, should either pass, the check has failed and the base branch gains only an empty commit; `gh api repos/OWNER/NAME/actions/secrets` must be refused, and, with a name made for the check that no secret can already hold, `name=PLACKET_CUSTODY_CHECK_$(openssl rand -hex 16); gh secret set "$name" --repo OWNER/NAME --body x && gh secret delete "$name" --repo OWNER/NAME` must stop at a refused `set`, so the agent's credential can neither read nor change the repository's Actions secrets (should the `set` pass, the check has failed, and the `delete` removes the secret it made, so it overwrites none and leaves none behind); and reading the applier's token or key, the mediator's key, the deciding role's key, `apply.sh`, `applied.jsonl` and the founding set file must fail. Repeat the check after any change to the ruleset, the App or the accounts.
